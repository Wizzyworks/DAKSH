# Skill Gap Analysis: Market Research & Improvement Strategy

## 1. What Your Frontend Currently Does (The Baseline)

The current approach follows this sequential flow:

```
CV Upload → AI Scanning (Simulated) → 10 Static MCQs → Score + Course Recommendations
```

**Core Limitation**: The questions are hardcoded per user profile (`amit_mondal`, `suparna_chatterjee`) in `mockData.js`. This is a prototype UX flow, not a real adaptive engine. The entire intelligence is mocked. For a real backend, you need to decide **which of the following paradigms** you want to actually build.

## 3. Is Your Current Approach Optimal?

**Short Answer: The CV upload is a solid entry point, but the static 10-MCQ approach is the weakest link.**

Here's a breakdown of what the market says works vs. what your frontend simulates:

### ✅ What You're Doing Right
- **CV as the starting point** is industry standard — everyone does it. The key is what you extract from it.
- **Role-to-competency mapping** (your FRAC framework) is conceptually correct — mapping a target role to required competency units is exactly what Eightfold and Gloat do.
- **Personalized course recommendations** post-assessment is the right endgame.

### ❌ Where Your Current Approach is Weak

**Problem 1: Static MCQs**
Your 10 questions are hardcoded per officer. In the real world, questions should be:
- Dynamically generated by an LLM based on the specific skills gap found in the CV
- Adaptive — if you answer Q3 correctly, Q4 should be harder in that domain

**Problem 2: MCQs alone have low validity for technical domains**
MCQs test *recognition* (can you identify the right answer when shown options?), not *recall* or *application*. For technical fields, this means a candidate can guess or eliminate. Pluralsight, iMocha, and Adaface all go beyond MCQ.

**Problem 3: CV parsing is only as good as the CV**
If a user underreports or overreports experience, your gap analysis starts from a corrupted baseline. The market is moving toward **multi-signal inference** instead of trusting CV text alone.

## 4. Better Approaches for Technical/Domain Skill Gap Analysis

Below are evaluation methods ranked from most to least feasible to implement as a backend feature:

### 🥇 Approach A: Adaptive MCQ Engine (Best Feasible Upgrade)
**How it works**: Instead of 10 fixed questions, use an Item Response Theory (IRT) / adaptive algorithm.
- Start with a medium-difficulty question
- If the user answers correctly → serve a harder question in that competency area
- If incorrect → serve an easier question to calibrate the floor
- After ~10-15 questions, you have a precise "competency score" per skill, not just a total score

**Who does this**: Pluralsight (Skill IQ), GRE, GMAT

**Backend requirement**: A question bank with difficulty ratings per competency. An IRT or simple ELO-style scoring algorithm. LLM to generate questions on-the-fly per difficulty level.

**Effort**: Medium. You can prompt Gemini/GPT to generate questions at "beginner / intermediate / expert" levels per topic.

---

### 🥈 Approach B: JD-Anchored Gap Analysis (Most Practical for Job Seekers)
**How it works**: Instead of assessing against a generic role (e.g., "Data Analyst"), you let the user paste in a specific Job Description URL or text. Your backend then:
1. Parses the JD to extract required skills (using NLP/LLM)
2. Compares extracted JD skills against the skills found in the CV
3. Surfaces a precise delta: "JD requires Kubernetes + Terraform, your CV shows neither"
4. *Then* generates targeted questions ONLY for the missing skills

**Who does this**: JobMatchAI, Skillora.ai, Resumly.ai

**Why it's better**: You're not testing generic domain knowledge — you're testing the *exact* gap between this user and this job. Much higher signal-to-noise ratio.

**Backend requirement**: JD parser (LLM), CV parser, skill entity extraction, semantic matching (cosine similarity or LLM comparison). This is very buildable with modern LLMs.

---

### 🥉 Approach C: Portfolio / GitHub Signal Analysis
**How it works**: User provides GitHub profile URL. Backend:
1. Fetches repos via GitHub API
2. Analyzes languages used, repo topics, README descriptions, commit history
3. Infers skills from *actual demonstrated work*, not self-reported text
4. Compares inferred skills against target role requirements

**Who does this**: Adaface (partially), some internal hiring tools

**Why it's powerful**: You're reading *evidence of skill*, not claims. A candidate who says "I know React" but has zero React repos has a very different profile than one with 5 React projects.

**Backend requirement**: GitHub API integration, language + topic analysis, LLM to interpret README/code context, semantic matching against role taxonomy.

---

### 🏅 Approach D: Multi-Signal 360° Inference (The "Gold Standard")
Combine all of the above:
```
CV Text + GitHub Portfolio + JD Target + Adaptive MCQ → Unified Skill Profile
```
Each signal contributes to a confidence-weighted skill score. This is what Eightfold AI does at enterprise scale. **This is likely overkill for a hackathon but is the long-term vision.**

## 5. Recommended Enhanced Pipeline for Your Backend

Given you're building a real backend for this project, here's the pragmatic recommended architecture:

```
Phase 1 — CV Parsing
  └── Extract text from PDF/DOCX (PyMuPDF or python-docx)
  └── LLM prompt: "Extract skills, years of experience per skill, and domain from this text"
  └── Output: { skills: [...], domain: "...", experience_level: "..." }

Phase 2 — Target Role Mapping
  └── User selects target role OR pastes a Job Description
  └── LLM prompt: "Extract required skills from this JD, categorize as mandatory vs. nice-to-have"
  └── Output: { required_skills: [...], preferred_skills: [...] }

Phase 3 — Gap Computation
  └── Set difference: required_skills - user_skills = GAP
  └── Semantic matching (not just string equality — "React.js" matches "ReactJS")
  └── Output: { skill_gaps: [...], strength_areas: [...], gap_score: % }

Phase 4 — Adaptive Assessment
  └── LLM generates questions ONLY for gap skills, at appropriate difficulty
  └── Adaptive: correct answer → harder next question, wrong → easier
  └── Output: { competency_score_per_skill: {...}, confirmed_gaps: [...] }

Phase 5 — Course Recommendation
  └── Map confirmed_gaps to course catalog
  └── Rank by: impact on gap closure × course rating × time-to-complete
  └── Output: Personalized learning roadmap
```

## 6. Summary: What to Build vs What to Skip

| Feature | Priority | Why |
|---|---|---|
| Real CV parser (PDF/DOCX text extraction) | **Must Have** | Foundation of everything |
| LLM-based skill entity extraction from CV | **Must Have** | Core intelligence layer |
| JD skill extraction + Gap computation | **Must Have** | This is the real differentiator |
| Semantic skill matching (not keyword) | **Must Have** | "ML" ≠ "Machine Learning" is a mistake |
| Dynamic LLM-generated questions per gap | **Should Have** | Much better than static MCQ bank |
| Adaptive question difficulty (IRT/ELO) | **Nice to Have** | More accurate scoring |
| GitHub API portfolio analysis | **Nice to Have** | Strong differentiator if time allows |
| Multi-signal 360° fusion | **Future Scope** | Enterprise-grade, not for v1 |

> [!IMPORTANT]
> The single biggest upgrade over your current frontend simulation is replacing the static MCQ bank with **LLM-generated questions dynamically calibrated to the specific skill gap found in the user's CV vs. their target JD**. This alone makes the feature genuinely intelligent rather than just well-designed.

> [!TIP]
> For the tech stack: Python (FastAPI) + LangChain/LlamaIndex + Gemini Pro or GPT-4o for the LLM layer. Use PyMuPDF for PDF parsing. For semantic skill matching, a small embedding model (sentence-transformers) is fast and cheap enough to run locally.
